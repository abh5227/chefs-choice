Chef’s ChoiceChef’s Choice

A recipe app that keeps the author’s recipe + and writes my changes in the margin.

I designed and built Chef’s Choice, a recipe app, with Claude Code. It holds my own collection of 301 recipes, most of them imported from another recipe app. Each recipe keeps the author’s version, and the app records my edits and cooks on top of it. The app on this page is its real front end, running in your browser on three sample recipes.

What it holds

  • 301 recipes from my own collection
  • about 10,000 ingredients in the library
  • imports from another recipe app’s export, a web address, or a saved page

How it’s built

  • 6,105 Python and 793 JavaScript tests passing
  • 64 schema migrations
  • 19 written release records

The server is Flask and SQLAlchemy on SQLite, and Alembic keeps a matching Postgres schema that the tests check. The page is plain JavaScript built with Vite, with Tiptap for editing a recipe’s steps. GitHub Actions runs the tests, and SonarQube scans the code.

Recipes counted 24 Nov 2026 and tests 16 Nov 2026. The release records are dated 1 Oct–25 Nov 2026.

The recipe

Inside the app

An importer that fixes by rule

Recipes come in from another recipe app’s export, a web address, or a page saved from a site that blocks importers. Each cleanup is a rule in code, so the same fix reaches every recipe I already have and every one I import next. The app flags any line no rule can decide, so a person checks it and the importer never guesses.

Try this Pick a line with a bar down its left edge, and find its reason in the list under the table.

Scaling that reads like a cook

Halve the cake and ¾ cup of oil becomes 6 tbsp, while 1 tbsp of zest becomes 1½ tsp. Eggs, bay leaves, and chicken thighs stay whole. The same rules run in Python on the server and in JavaScript on the page. A test checks that both sides use the same numbers and unit names, so the two never print different amounts.

Try this Press ½× and watch ¾ cup of oil become 6 tbsp.

An ingredient library that knows what cooks call things

The app matches recipe lines to a library of about 10,000 ingredients, drawn mostly from Wikidata and Open Food Facts. Nearly 6,000 of them link to a Wikidata entry. The library also knows other names cooks use, so “green onion” finds scallion, “confectioners’ sugar” finds powdered sugar, and “gochugaru” finds Korean red pepper flakes.

Waits shown before the first step

The app stores marinating, chilling, rising, and soaking as entries of their own, and each one can link to the step it belongs to. The Total counts the waits that always apply. An optional wait, like the beans’ overnight soak, gets a second total of its own, so a cook can see what that path costs.

Try this Compare the Total, 1 hr 40 min, with the line under it, which adds the overnight soak.

Notes that belong to steps

A note has a type and can belong to a step. It shows as a tag on that step and again under Step notes. A note that mentions “step 2” links to that step, and the link follows it when a cook reorders the steps.

Try this Press the NOTE tag on step 5 to open the tip about chicken breasts.

Your changes, in the margin

Each recipe keeps a saved copy of how it arrived, and the page shows the cook’s changes in a handwritten layer over the print. A cook’s edits never touch that copy. A repair script updates the recipe and its saved copy in one step, so the marks show only the cook’s own edits.

Try this Find the sugar, where the cook’s ¾ cup is inked over the printed 1 cup.

A rating belongs to a cook

Cooked it logs today’s cook in one tap. Log a past cook takes a date from a calendar and a rating in half stars. The recipe shows the average of the rated cooks, and a cook left unrated does not pull the average down. Undo takes the last cook back off.

Try this Press Cooked it, rate the cook, then press Undo to take it back off.

An album for every dish

Every photo of a dish goes in its album, at the foot of the recipe. The album is a mosaic that keeps each photo whole, at its own shape, in the order the cook set. One photo is the Hero, the recipe’s cover, which sits at the top as a Polaroid and carries a ★ Hero mark in the album.

Try this Find the ★ Hero mark in the album, then click that photo to see it large.

How much of the collection links to the library

Of 3,355 ingredient lines, 2,975 link to the library, most of them through Wikidata.

Of 3,355 ingredient lines, 2,209 link to a Wikidata entry. 346 link to an Open Food Facts entry, and 420 to an entry I wrote. 380 lines are not linked.

The 2,975 links point to 433 different entries, in a library of 10,023. Each entry comes from Wikidata or Open Food Facts, or is one I wrote and keep in a file of its own.

A line is one ingredient row in a recipe, not a heading. An entry’s id shows where it came from, a Q number for Wikidata, en: for Open Food Facts, or a plain name for one I wrote.

What I learned

Keep the author’s recipe and the cook’s changes apart.

The app shows a cook’s edits by comparing each recipe with a saved copy of how it arrived. That copy is the only record of the author’s words, so I treat it as permanent. Notes had to come out of it, so they went first into a table of their own, and none of the author’s words were lost.

Declare a data change before making it.

Cleanup scripts in September changed recipes without updating the saved copy, so 27 of 49 edit marks showed the scripts’ work as a cook’s. I learned that a mark is only as true as the copy behind it. Now a standing check stops any data change that moves a recipe or its saved copy without declaring it first.

Make a test hold Python and JavaScript equal.

The JavaScript scaler and two Python readers each kept their own list of units, and nothing checked that the lists matched. 205 amounts like “1kg” were read as plain counts, and 77 of them printed the wrong figure when scaled. I learned that two pieces of code reading the same text drift apart unless a test holds them together. Now Python and JavaScript hold the same 52 units, and a test fails the moment they differ.

Look at the page as well as the tests.

In October, the first build of the two-column time block threw no error and still dropped the scaling control from 78 of my 300 recipes. I learned that tests check what I thought to ask, and the page shows what a cook gets. Now every visible change gets a click-through in the browser before release.

Turn repeated one-off answers into rules.

One cleanup round gave 111 answers one line at a time, for lines its rules could not decide. I asked Claude to read the answers together, and lines like “1 tsp EACH garlic powder, onion powder, dried oregano” turned up five times. The answers had read each one as a choice, when it lists several ingredients sharing one amount. I learned that one-off answers that repeat a shape are a rule waiting to be written. Now the importer splits such a line into one line per ingredient, each with the shared amount.

Rehearse on a copy and keep a way back.

A release runs on a copy of the database first, and a check compares the result with the declaration cell by cell. On release day, I back up the real database the moment the server stops and keep a copy of the result. Before any rollback, I compare the live database with that copy, so a cook’s later entries are never lost by accident.

I designed the product and directed the engineering. I decided what the app does and how it looks, and I approved every change to my real data before it ran. Claude Code wrote the code from plans I approved, and I set up the release process above.
